## Reprise ciblée des évaluations

Le nouvel outil `acquisition_plan_retry_assessment` permet de reprendre uniquement un canal échoué, sans relancer l’étude. Le passage de failed à pending et le job sont atomiques dans le service partagé HTTP/MCP. Le worker transmet l’intention manuelle du retry jusqu’à la nouvelle campagne, même si l’étude d’origine est ancienne. Le même requestKey ne queue qu’un job. Cette tranche est testée en PostgreSQL ; reprise réelle en attente du compte de validation.

La revue a fait ajouter une persistance sur l’évaluation : migration additive `0117_assessment_activation_mode` (colonne nullable, contrainte manual/null, sans backfill). Un retry HTTP ultérieur conserve la consigne du précédent retry MCP. Le test couvre MCP → échec → reprise du service HTTP → worker → campagne draft/manual. Le code d’erreur d’évaluation absente/non échouée est vérifié via un vrai client SDK MCP. Revues Spec et Standards terminées sans défaut restant ; migration testée sur la base d’intégration isolée, TypeScript et 14 tests/95 assertions passent.
